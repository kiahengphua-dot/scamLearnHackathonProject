# ScamLearn

**Learn to spot the scam before the scam spots you.**

Built for HackSocial 2026.

## Problem

Scam-detection tools (e.g. Singapore's ScamShield) tell people *what* is dangerous.
They don't teach people *how to think* when they're under social pressure — which
is the actual moment a scam succeeds or fails.

## What ScamLearn does differently

ScamLearn doesn't ask "is this a scam?" It puts you inside a simulated
conversation — a fake bank alert, a "recruiter," a "family member" in
trouble — and lets you respond however you would in real life. Your choices
drive the conversation. At the end, ScamLearn reveals whether it was a scam
or legitimate, scores *how you reasoned* (not just whether you guessed
right), and replays exactly where you could have caught it.

- **Training Mode** — practice against a named manipulation technique with the
  learning objective shown up front.
- **Test Mode** — you're not told anything in advance. Could be a scam, could be
  legitimate. Investigate, don't assume.

## Current status

- **Phase 1 — Core Scenario Engine:** deterministic schema, loader, state
  machine, server-side scoring, and 6 demo scenarios.
- **Phase 5 — Claude Roleplay Integration:** scenario dialogue is now
  dynamically generated by Claude, forced through a structured tool call so
  it can only ever return a message, a dramatic intent, and a technique tag
  — never a score, classification, or outcome. If the API key is missing,
  the call fails, or the response is malformed, the app falls back to the
  scripted message from Phase 1 and keeps working.
- **Artifact Analysis:** paste a suspicious message, upload a screenshot, or
  submit a URL, and Claude reports evidence-based indicators (never a flat
  verdict), then can generate a fictionalized training scenario from those
  techniques — which plays through the exact same deterministic engine as
  the 6 static demo scenarios. Raw artifacts (image bytes, pasted text,
  fetched page content) are never persisted — only the derived analysis is
  stored.
- **URL analysis:** the server fetches the submitted URL itself, hardened
  against SSRF (private/loopback/link-local/cloud-metadata addresses
  blocked, redirects re-validated per hop, response size capped, no
  JavaScript execution) — see Security & privacy below.
- **Scam Replay:** every completed session has a turn-by-turn replay
  (`GET /api/sessions/<id>/replay`) reconstructed entirely from stored
  messages/decisions — the manipulation technique per stage, what you did
  well vs. missed, and an intervention point ("this is where you could
  have caught it" or "this is where you did"). Claude adds a short,
  non-judgmental narrative and one lesson to remember on top, with a
  templated fallback if it's unavailable.
- **Personalized recommendations:** `/api/profile` returns overall
  proficiency, strongest/weakest category, and a concrete next scenario
  targeting the weakest one — derived directly from each scenario's own
  `scoring_rules` categories, not a hardcoded mapping.
- **Achievements:** a small set of deterministic, backend-awarded badges
  (first completion, avoided a scam, perfect score, resisted an advanced
  scenario, correctly handled a legitimate one, trained against your own
  submitted artifact). Prototype/local only — no real vouchers.
- **Rate limiting:** in-memory, per-IP limits on the Claude-calling and
  URL-fetching endpoints, so a script can't run up API costs or use the
  URL endpoint to probe internal network reachability by volume.

Not yet built: UI polish is only partial (functional pages, minimal
animation). No enterprise/admin dashboard, no real payment/voucher
integration — both intentionally out of scope per the spec's MVP priority.

**Known limitation:** free-text scoring (both static and generated
scenarios) relies on keyword matching, not semantic understanding. For
generated scenarios in particular, the "dangerous"/"safe" phrases are
freshly authored per artifact and narrower than the hand-tuned static
scenarios' keyword lists — a user who falls for the scam in their own
words, rather than close to one of the generated phrases, won't trigger
the terminal condition. This is a real gap, not hidden by design.

## Architecture

```
Browser (HTML/CSS/vanilla JS)
    | anonymous signed cookie (no login)
Flask backend
    |- scenario engine (deterministic — owns state, stage progression, scoring, outcome)
    |- AI layer (app/ai/ — Claude roleplay, forced structured output, scripted fallback)
    |- SQLite (sessions, messages, decisions, skill profiles)
```

The backend is always the source of truth for scenario classification,
scoring, stage progression, and outcomes. Claude only narrates whichever
stage the backend has already decided to move to — it has no field in its
response through which it could skip a stage, assign a score, or reveal
classification. See `app/scenarios/schema.py`, `app/engine/`, and `app/ai/`
for the full logic.

### The Claude roleplay contract (`app/ai/`)

- `claude_client.py` — thin wrapper around the Anthropic SDK; a single call
  forced through a tool (`tool_choice`), catches all exceptions, never raises
- `prompts.py` — builds the system prompt (fixed) and message history, with
  the user's latest text always wrapped in an explicit "USER MESSAGE
  (untrusted)" block, never concatenated as instructions
- `schemas.py` — the `provide_roleplay_response` tool schema
  (`message`, `roleplay_intent`, `technique_used` only, `additionalProperties: false`)
  and validation of its output
- `roleplay.py` — orchestrates one turn: try Claude, validate, retry once,
  and fall back to the Phase 1 scripted message on any failure

Claude is never called for a terminal decision (STOP/REPORT, a dangerous
keyword trigger, or an already-completed session) since there's no message
left to narrate — the scenario engine settles those before AI is ever
consulted.

### Artifact analysis and scenario generation (`app/artifacts/`)

```
ARTIFACT (pasted text / screenshot, never persisted)
    -> analysis.py    -- Claude reports evidence (indicators/confidence), forced tool call
    -> stored: only the derived analysis, in artifact_analyses
    -> scenario_generator.py -- Claude proposes narrative content (title, stage
       messages, red flags, phrases); ALL scoring mechanics (deltas, terminal
       flags, base_risk) are assembled in plain Python, exactly like the
       roleplay layer keeps Claude out of scoring during live play
    -> validated through the SAME app.scenarios.schema.validate_scenario_dict()
       every static scenario goes through, plus a real-entity denylist check
    -> stored in generated_scenarios, playable via the existing
       /api/sessions endpoint exactly like a static scenario
```

Claude only ever supplies flavor text here too — never a validated scenario's
scoring table. If generation fails validation or trips the denylist twice,
the honest response is "couldn't generate a scenario," not a silent
fallback to fabricated content (there's no scripted version of an arbitrary
user's own artifact to fall back to).

Test Mode never plays a user's own generated scenario — since they already
know what they submitted, that would defeat the blind-test premise. It's
restricted to the 6 curated static scenarios.


## Scenario schema

Each scenario is a JSON file (`app/scenarios/data/*.json`) validated at
startup against `app/scenarios/schema.py`. Key fields:

- `classification`: `SCAM` or `LEGITIMATE` — server-side only, never revealed until the scenario ends
- `allowed_stages`: an ordered subset of `CONTACT → RAPPORT → CREDIBILITY → MANIPULATION → REQUEST → ESCALATION` (`RESOLUTION` is implicit)
- `script`: the scripted message for each stage after the first
- `scoring_rules`: a configurable table mapping `action:*` / `keyword:*` triggers to score deltas, categories, and explanations
- `trigger_keywords`: keyword lists used to detect what a user's free-text response actually did (e.g. shared an OTP)

## Scoring

Every scenario ships its own `scoring_rules` table. Each user decision
(action button + optional free text) is matched against the scenario's
action-based and keyword-based triggers; the backend computes the score
delta from that table — the AI (once integrated) will never assign points
directly. A score starts at 50/100 and is clamped to [0, 100]. See
`app/engine/scoring.py`.

## Security & privacy

- The Anthropic API key lives only in `.env`, is read server-side, and is
  never sent to the browser, returned by any API endpoint, or written to logs.
- Every user message is treated as untrusted dialogue, not instructions —
  the roleplay prompt explicitly wraps it as such and instructs Claude to
  never break character or reveal a scenario's classification, no matter
  how the request is phrased (see `app/ai/prompts.py`).
- Claude's response is forced through a tool schema that structurally
  cannot carry a score, classification, or outcome — those fields don't
  exist in the schema at all.
- Uploaded screenshots are read in memory, base64-encoded for the Claude
  vision call, and discarded — never written to disk. File type and size
  are validated both by the app (per-field checks) and by Flask's
  `MAX_CONTENT_LENGTH` (a hard 413 before the body is even fully buffered).
- Generated scenarios are checked against a real-entity denylist (common
  bank/payment/tech brand names) before ever being shown to a user, on top
  of the prompt instruction to fictionalize everything — the same
  don't-rely-on-the-model-alone principle applied throughout.
- No login system — an anonymous, signed, HttpOnly cookie identifies a demo
  user for session and skill-profile continuity.
- All scoring, outcomes, and classification are computed server-side; the
  client only ever sends an action type and free text.
- Security headers (`X-Content-Type-Options`, `X-Frame-Options`,
  `Referrer-Policy`) are set on every response.
- User-entered and scenario text is rendered via `textContent`, never
  `innerHTML`, in the frontend.
- **URL fetching (`app/artifacts/url_fetcher.py`) is SSRF-hardened**: only
  `http`/`https` on default ports; every resolved IP is checked against
  private/loopback/link-local/reserved/multicast ranges (blocks
  `169.254.169.254`, `127.0.0.1`, `10.0.0.0/8`, etc.); redirects are
  intercepted and re-validated on every hop rather than auto-followed;
  response size is capped while reading, not just via headers; no
  JavaScript execution or headless browser. Every failure mode (SSRF
  block, DNS failure, timeout, oversized response) returns the same
  generic error to the client — differentiating them would let the
  endpoint be used to map internal network topology by response pattern.
- Rate limiting (`Flask-Limiter`, in-memory) on `/api/artifacts/analyze`,
  `/api/artifacts/<id>/generate-scenario`, and `/api/sessions/<id>/decisions`
  — the three endpoints that either cost real API spend or make an
  outbound network request on the user's behalf.

## Installation

```
git clone <this-repo>
cd HackSocial
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt
copy .env.example .env        # then fill in ANTHROPIC_API_KEY and FLASK_SECRET_KEY
```

## Running locally

```
python run.py
```

Then open `http://127.0.0.1:5000`.

## Running tests

```
python -m pytest tests/ -v
```

The test suite never makes real Anthropic API calls — `app.ai.claude_client`
is monkeypatched in `tests/test_ai_roleplay.py`, and the default test config
runs with an unconfigured API key so the rest of the suite exercises the
scripted fallback path.

## Limitations

This is an educational prototype, not a scam-detection product. It does not
guarantee protection from real scams, and its AI simulation (once added)
will not perfectly represent real-world attackers. The purpose is
behavioural training, not certified security software.
